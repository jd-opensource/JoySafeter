# 中文界面 Draft 术语调整设计

## 背景

当前中文界面将产品中的可编辑版本统一称为「草稿」。这个词语义准确，但口语感偏强，也容易传达出“临时、不正式、质量较低”的印象。对于当前产品面向的非技术用户，这种措辞不够稳妥。

代码内部、接口字段、状态机和英文文案已经稳定使用 `draft` 语义。为了避免扩大变更面，本次调整只处理用户可见的中文界面表述，不触碰内部技术概念。

## 目标

- 将所有面向用户的中文 UI 文案中的「草稿」统一调整为「初版」
- 清理中文 locale 中残留的英文 `Draft`，保证中文界面表述一致
- 保持内部代码语义、接口字段、英文 locale、测试命名不变

## 非目标

- 不修改任何内部标识、类型、接口字段或数据库状态值
- 不修改英文 locale 中的 `Draft`
- 不批量修改历史 spec、设计文档、测试描述或注释
- 不重命名 i18n key

## 变更范围

仅修改文件：

- `frontend/lib/i18n/locales/zh.ts`

该文件中凡是用户可见、且表达产品 UI 语义的「草稿」或残留英文 `Draft`，都纳入本次调整。

## 设计原则

### 1. 产品语言与技术语义分层

前端展示文案允许使用更适合用户理解的词汇，但内部实现继续保留 `draft` 作为技术语义。这样可以避免将状态机、接口契约和历史实现一起卷入术语重构。

### 2. 语境优先，不做机械替换

替换目标是“读起来自然”，不是逐字替换。因此相同术语在不同语境中允许按句意调整，只要最终用户看到的语义统一指向「初版」。

### 3. 只改 value，不改 key

i18n 的 key 仍保留原状，例如 `runDraft`、`savedDraft` 等不重命名。这样可以把变更限制在展示层，避免引入调用方回归。

## 替换规则

优先按下面的语义规则替换：

| 场景 | 当前文案 | 目标文案 |
|------|----------|----------|
| 单独名词 | 草稿 | 初版 |
| 动作短语 | 运行草稿 | 运行初版 |
| 动作短语 | 生成草稿 | 生成初版 |
| 状态短语 | 草稿已保存 | 初版已保存 |
| 状态短语 | 草稿已变更 | 初版已变更 |
| 标题说明 | 测试当前草稿 | 测试当前初版 |
| 中英混排 | Restore Draft | 恢复初版 |
| 中英混排 | 当前 Draft | 当前初版 |

如果某些句子直接替换后不够自然，应优先保留句子通顺。例如：

- `发布前先运行草稿行为` -> `发布前先运行初版行为`
- `输入一个用于测试草稿的请求...` -> `输入一个用于测试初版的请求...`

## 实施方式

1. 检查 `zh.ts` 中所有包含「草稿」或 `Draft` 的用户可见文案
2. 按语境逐条改写为「初版」
3. 保留英文 locale、后端字段、测试命名和状态枚举不变
4. 修改后重新检索 `zh.ts`，确认没有遗留的用户可见「草稿」或 `Draft`

## 风险与控制

### 风险 1：误改内部技术语义

如果做全仓库替换，会误伤 `draft` 状态字段、测试命名、服务方法和领域概念。

控制措施：

- 只修改 `frontend/lib/i18n/locales/zh.ts`
- 不改任何 key、代码标识或英文 locale

### 风险 2：文案机械替换后不自然

部分句子里的「草稿」是说明性语言，不一定适合直接逐字替换。

控制措施：

- 按完整句意检查
- 允许局部重写，但保持“初版”作为统一称呼

### 风险 3：中文界面残留英文 Draft

即使中文文案主体已经替换，仍可能存在少数英文按钮或提示，造成术语不一致。

控制措施：

- 同时检索 `草稿` 与 `Draft`
- 将中文 locale 内的残留英文标签一并改成中文

## 验收标准

- 中文界面不再出现面向用户的「草稿」或 `Draft`
- 英文 locale 不发生变化
- 内部字段、接口、状态机、测试语义不发生变化
- 文案自然可读，不出现明显生硬替词

## 实施后验证

- 对 `frontend/lib/i18n/locales/zh.ts` 做静态检索自查
- 如有低成本前端校验命令，可运行最小范围验证
- 若无现成低成本校验，至少完成文本级人工复核
