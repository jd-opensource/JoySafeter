# Global Typed ID Unification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Eliminate duplicate, weakly typed, and compatibility-based entity-ID handling across Python, Rust, runner, CLI, frontend, persisted data, and documentation.

**Architecture:** Python uses one dependency-light `EntityId` family plus a separate SQLAlchemy adapter. Both Rust workspaces use one shared typed-ID crate. Public and persisted boundaries accept only canonical prefixed IDs; physical UUID conversion is explicit and allowlisted. Entity IDs are generated by the use case that creates the entity, not implicitly during ORM flush.

**Tech Stack:** Python 3.13, Pydantic v2, SQLAlchemy 2, Alembic, Rust, Serde, SQLx, TypeScript, React, Vitest

**Spec:** `docs/superpowers/specs/2026-08-24-global-typed-id-unification-design.md`

## Global Constraints

- Inspect every caller before changing an ID type or conversion; no mechanical repository-wide replacement.
- Preserve unrelated uncommitted files and do not modify `.deps/SkillSpector`.
- Run Python pytest commands from `backend/`.
- Do not commit unless the user explicitly requests it.
- Bare UUIDs remain only at reviewed PostgreSQL, Redis, protobuf, telemetry, object-storage, third-party, and infrastructure-naming boundaries.
- Public and persisted legacy ID forms are removed, not retained behind compatibility fallbacks.

  Review every production constructor and add the matching `id=<Type>.new()` at

  and idempotent replay. A retry creates a new entity ID only when it represents
  a new entity rather than the same idempotent operation.
